Linux 服务检查、启动与排障

知知行笔记·2026-10-22·约 19 分钟阅读
linuxoperationsjavanginxredisnetworktroubleshooting

从历史排障记录提炼的通用操作方法，适用于检查 Java 应用、Nginx、Redis 和数据库等服务。本文不绑定项目、服务器地址或固定部署目录，也不表示已对当前服务器执行验证。

文中 <服务单元名>、<端口>、<服务器IP>、<应用目录> 等均需替换；包含占位符的命令不能原样执行。命令按用途分别选用，不需要从头全部执行。

每组命令下方附有具体示例。示例统一使用虚构服务 demo-api、目录 /opt/demo-api 和文档专用 IP 192.0.2.10，执行前换成实际值；示例输出仅用于说明判断方法。

1. 判断服务正常，要检查到哪一层

层次 检查内容 能证明什么 仍不能证明什么
进程 ps、pgrep、jps 相关进程存在 启动完成、端口可用
监听 ss 指定进程监听指定地址和端口 外部网络可达、业务正常
网络 nc、Test-NetConnection 客户端能够建立 TCP 连接 认证通过、协议正确
协议 HTTP 响应、Redis PING、数据库查询 对应协议或简单操作成功 全部业务功能正常
业务 登录、读取列表、必要的读写验证 验证过的业务链路可用 未覆盖的其他功能正常

建议顺序：进程 → 监听地址和端口 → 本机协议验证 → 远程连接 → 业务验证。不要因为看到 Java 进程就宣布启动成功，也不要因为后端根路径返回 404 就认定服务退出。

2. 先查看状态，避免重复启动

systemd 管理的服务

systemctl status <服务单元名> --no-pager
systemctl is-active <服务单元名>
journalctl -u <服务单元名> -n 100 --no-pager

示例：查看名为 demo-api.service 的服务状态和最近100条日志。

systemctl status demo-api.service --no-pager
systemctl is-active demo-api.service
journalctl -u demo-api.service -n 100 --no-pager

is-active 返回 active 表示单元处于活动状态；failed 表示失败，继续查看上面的日志。单元处于活动状态仍需验证端口和业务接口。

如果服务由 systemd、容器或其他进程管理器托管，应通过原管理方式操作。不要再手动启动一份相同应用；手动杀进程后，管理器还可能自动拉起新进程。

普通进程及资源

ps -ww -eo pid,ppid,stat,comm,args
pgrep -af java
jps -lv
free -h
df -h
du -sh <应用目录>

示例：筛选应用、核对 Java 启动参数，并检查内存、磁盘和应用目录占用。

ps -ww -eo pid,ppid,stat,comm,args | grep '[d]emo-api.jar'
pgrep -af java
jps -lv
free -h
df -h
du -sh /opt/demo-api

例如进程输出含 24680 java -jar /opt/demo-api/demo-api.jar，表示 PID 为24680；du 输出 320M /opt/demo-api，表示该目录占用约320MB。free 的 available 假设为 5.2Gi，表示估计仍可供新应用使用的内存约5.2GiB。

jps 需要可用的 JDK 工具和足够权限；看不到进程不能单独证明应用不存在。判断具体应用时核对完整命令、JAR 路径和 PID，不要只依赖进程短名称。free -h 重点看 available，df 看文件系统空间，du 看目录占用。

3. 核对端口、绑定地址与进程归属

sudo ss -lntp
sudo ss -lntp 'sport = :<端口>'
ps -ww -p <PID> -o pid,ppid,stat,comm,args

示例：查看8080端口归属，并核对查到的24680号进程。

sudo ss -lntp
sudo ss -lntp 'sport = :8080'
ps -ww -p 24680 -o pid,ppid,stat,comm,args

假设结果包含 0.0.0.0:8080 和 pid=24680，表示该进程监听全部 IPv4 本地地址的8080端口；若为 127.0.0.1:8080，则只监听回环地址。

以上是 TCP 监听检查；UDP 使用 ss -lnup。需要较高权限才能完整显示其他用户的进程信息。

监听地址 常见含义
127.0.0.1 仅本机回环访问
某个具体网卡 IP 监听该地址；不能假定 127.0.0.1 也可连接
0.0.0.0 监听全部 IPv4 本地地址
[::] IPv6 通配监听；是否同时接受 IPv4 需结合系统和应用配置确认

服务提示端口占用时，先查监听 PID 和完整命令，再决定处理方式。进程退出和端口释放可能存在时间差；不要立即重复启动或根据旧 PID 直接结束进程。

4. 区分网络问题、认证问题和业务问题

Linux 客户端检查 TCP：

nc -vz -w 3 <服务器IP> <端口>

示例：从当前 Linux 机器测试目标服务器的8080端口，最多等待3秒。

nc -vz -w 3 192.0.2.10 8080

输出 succeeded 或 open 一类信息通常表示 TCP 连接成功，具体文字取决于本机 nc 实现；不能据此认定登录或业务接口正常。

Windows PowerShell 检查 TCP：

Test-NetConnection <服务器IP> -Port <端口>

示例：从 Windows 开发电脑测试同一端口。

Test-NetConnection 192.0.2.10 -Port 8080

重点看 TcpTestSucceeded：True 表示本次 TCP 连接成功，False 表示失败。

nc 的选项以本机实现为准，未安装时可先使用对应协议客户端验证。

现象 优先检查
Ping 成功，TCP 失败 监听地址、端口、防火墙、安全组、路由；Ping 不代表应用端口可用
Connection refused 目标地址无监听，或中间设备主动拒绝
连接超时 路径不通、过滤规则丢弃、服务无响应等；不能仅凭超时确定根因
TCP 成功但认证失败 账号、密码、来源授权、TLS 和服务端配置
HTTP 401/403/404/405 已收到 HTTP 响应；核对认证、路径、方法及响应是否来自预期服务
HTTP 502/504 已到达代理；继续检查上游地址、连接、超时和后端日志

5. 使用协议验证服务

HTTP

curl -I --connect-timeout 3 --max-time 5 http://<服务器IP>:<端口>/
curl -i --connect-timeout 3 --max-time 5 http://<服务器IP>:<端口>/<只读检查路径>

示例：检查首页响应，再访问示例应用已实现的只读 /health 接口。

curl -I --connect-timeout 3 --max-time 5 http://192.0.2.10:8080/
curl -i --connect-timeout 3 --max-time 5 http://192.0.2.10:8080/health

例如首页返回404、/health 返回200及 {"status":"UP"}，说明首页路径不存在，但健康接口可响应。Windows PowerShell 如需调用系统 curl 程序，使用 curl.exe。

-I 发送 HEAD，请求路径不支持 HEAD 时改用只读 GET。优先使用服务实际提供的健康检查或只读接口；根路径可用于初步确认响应，但不能替代业务验收。

Redis

redis-cli -h <服务器IP> -p <端口> --askpass PING

示例：连接6379端口，按交互提示输入密码。

redis-cli -h 192.0.2.10 -p 6379 --askpass PING

预期响应为 PONG；若提示 WRONGPASS，重点核对认证配置，不能当作端口未开放处理。

返回 PONG 表示本次连接、认证和 PING 成功。使用 ACL 用户时补充 --user <用户名>；若启用 TLS，按实际配置使用 TLS 参数。避免把真实密码直接写进操作笔记。

MySQL

mysql -h <服务器IP> -P <端口> -u <用户名> -p

示例：用虚构的只读账号 demo_reader 登录，密码按提示输入。

mysql -h 192.0.2.10 -P 3306 -u demo_reader -p

看到 mysql> 提示符表示连接和登录成功；Access denied 表示需要继续核对账号、密码及来源授权。

连接后执行只读验证：

SELECT VERSION(), @@lower_case_table_names;
SELECT 1;

示例：登录后执行 SELECT 1;，结果应包含一行值 1；执行第一条查询若得到版本 8.0.x、lower_case_table_names 为 1，说明当前实例采用下文所述的小写名称策略。这里的版本和设置均为假设输出。

连接成功不代表该账号可以访问业务库，还应核对目标库、表和必要权限。lower_case_table_names=1 表示库表名按小写保存且名称比较不区分大小写；已有数据库的大小写策略不应作为普通故障修复直接改动。

其他数据库同样先用对应版本客户端连接，再执行只读查询；TCP 连通只完成了网络层检查。

6. Java JAR 的手动启动方式

仅用于没有被现有服务管理器托管、且确认未运行的应用。先确定 Java 路径、工作目录、配置环境、依赖连接和端口。

cd <应用目录>
nohup <JAVA_HOME>/bin/java \
  -Xms<初始堆大小> -Xmx<最大堆大小> \
  -Duser.timezone=Asia/Shanghai \
  -Dfile.encoding=UTF-8 \
  -jar <应用文件名>.jar \
  --spring.profiles.active=<环境名> \
  >> console.log 2>&1 < /dev/null &

示例：假设 Java 位于 /usr/bin/java，JAR 已放在 /opt/demo-api，且确认该应用尚未运行，启动8080端口的 Spring Boot 服务。

cd /opt/demo-api
nohup /usr/bin/java \
  -Xms256m -Xmx512m \
  -Duser.timezone=Asia/Shanghai \
  -Dfile.encoding=UTF-8 \
  -jar demo-api.jar \
  --spring.profiles.active=prod \
  --server.port=8080 \
  >> console.log 2>&1 < /dev/null &

控制台可能返回 [1] 24680，表示后台作业及进程信息，并不表示应用已启动成功。示例堆参数仅演示语法，生产值按实际资源确定；控制台日志写入 /opt/demo-api/console.log。

这是 Spring Boot 应用示例；普通 Java 应用的参数以自身实现为准。堆大小按负载和机器资源确定，还要为直接内存、线程栈、其他服务和操作系统留空间。--add-opens 等参数仅在应用确实需要时添加。

  • -Xms、-Xmx、-D... 是 JVM 参数，放在 -jar 前面。
  • JAR 后面的参数传给应用；Spring Boot 的 --spring.profiles.active 属于这一类。
  • >> 追加输出；2>&1 将标准错误合并到标准输出。
  • nohup 不负责开机自启、崩溃恢复或就绪检查，长期运行按现有管理机制维护。
  • 相对路径基于进程工作目录；这会影响文件配置、日志和数据文件的位置。

启动后检查本次新增日志、应用 PID、端口归属和只读接口。不要只凭后台命令返回成功判断应用已就绪。

7. Nginx 不在 PATH 中时怎么检查

command -v nginx 没有结果，不代表未安装。Nginx 可能随前端部署包放在自定义目录，先检查原服务单元或启动脚本。

command -v nginx
ps -ww -eo pid,ppid,stat,args | grep '[n]ginx'
<Nginx目录>/sbin/nginx -p <Nginx目录>/ -c conf/nginx.conf -t

示例：假设 Nginx 安装在 /opt/nginx，先查进程，再测试该目录下的配置。

command -v nginx
ps -ww -eo pid,ppid,stat,args | grep '[n]ginx'
/opt/nginx/sbin/nginx -p /opt/nginx/ -c conf/nginx.conf -t

配置检查输出含 syntax is ok、test is successful 表示测试通过；command -v 没有输出，只能说明当前 PATH 没有找到该命令。

配置检查通过且确认尚未运行后，再启动：

<Nginx目录>/sbin/nginx -p <Nginx目录>/ -c conf/nginx.conf

示例：确认尚未运行，且配置检查通过后启动同一实例。

/opt/nginx/sbin/nginx -p /opt/nginx/ -c conf/nginx.conf

命令无输出不等于业务验证通过，还应检查进程、配置中的监听端口和页面响应。

若由 systemd 管理，使用对应服务单元操作。若修改的是已运行实例，按原启动方式检查配置后 reload，保持正确的配置文件和 prefix，避免操作到另一套 Nginx。

8. Redis 的工作目录与地址

已有 Redis 启动前先读原配置，核对 bind、port、dir、日志路径及持久化配置。配置中的 dir ./ 等相对路径会受启动目录影响。

cd <Redis目录>
./bin/redis-server ./redis.conf

示例：Redis 安装在 /opt/redis，按该目录的配置启动。

cd /opt/redis
./bin/redis-server ./redis.conf

若配置为 dir ./，数据目录会相对于本次工作目录定位；因此不能随意换一个目录执行相同命令。是否进入后台取决于配置。

这是历史部署形态的示例，二进制可能位于 src/，也可能使用系统安装路径。是否后台运行取决于配置和托管方式。不要因为连接 127.0.0.1 失败就重启，先确认服务是否只绑定了某个网卡 IP。

9. firewalld 的逐步排查

仅适用于使用 firewalld 的机器；云环境还可能叠加安全组、网络 ACL 等规则。

systemctl is-active firewalld
sudo firewall-cmd --get-active-zones
sudo firewall-cmd --zone=<实际区域> --query-port=<端口>/tcp
sudo firewall-cmd --zone=<实际区域> --list-all

示例：假设活动网卡属于 public，检查8080端口及完整区域规则。

systemctl is-active firewalld
sudo firewall-cmd --get-active-zones
sudo firewall-cmd --zone=public --query-port=8080/tcp
sudo firewall-cmd --zone=public --list-all

例如返回 active，且区域列表显示网卡位于 public，才能按这个区域继续检查。--query-port 返回 no 时仍需查看完整规则。

--query-port 返回 no，不代表一定无法访问，还需查看 rich rule、服务规则等。区域应以实际网卡归属为准。

确认需要授权某个客户端访问后，可先添加来源受限的运行时规则：

sudo firewall-cmd --zone=<实际区域> \
  --add-rich-rule='rule family="ipv4" source address="<客户端IPv4>/32" port port="<端口>" protocol="tcp" accept'

示例：临时允许单台开发电脑 192.0.2.20 访问服务器8080端口。

sudo firewall-cmd --zone=public \
  --add-rich-rule='rule family="ipv4" source address="192.0.2.20/32" port port="8080" protocol="tcp" accept'

返回 success 后，从开发电脑重新测试连接。该例假设服务器实际看到的来源就是此 IP，经过 NAT 时应核对实际来源。

从该客户端重新测试。验证有效且需要长期保留时，再将同一条规则写入永久配置：

sudo firewall-cmd --permanent --zone=<实际区域> \
  --add-rich-rule='rule family="ipv4" source address="<客户端IPv4>/32" port port="<端口>" protocol="tcp" accept'

示例：临时规则验证有效，且确认需要长期保留时，补上同一条永久规则。

sudo firewall-cmd --permanent --zone=public \
  --add-rich-rule='rule family="ipv4" source address="192.0.2.20/32" port port="8080" protocol="tcp" accept'

返回 success 表示永久配置写入成功。这里已先添加运行时规则，不需要立即 reload。

运行时规则立即生效，重载或重启后通常失效；永久配置本身不会立即改变运行时。上面分别添加了两份相同规则，无需为了使刚添加的运行时规则生效而 reload。reload 前应检查其他尚未持久化的运行时规则。

若需求确实是向整个区域开放端口，可使用 --add-port=<端口>/tcp，但它不限定单个来源。不要把关闭整个防火墙作为常规解决方案。

10. 日志排障与 nohup.out

ls -l --time-style=long-iso <日志文件>
tail -n 100 <日志文件>
tail -f <日志文件>

示例：检查 Java 服务的日志修改时间，读取最近100行，再持续跟踪新日志。

ls -l --time-style=long-iso /opt/demo-api/console.log
tail -n 100 /opt/demo-api/console.log
tail -f /opt/demo-api/console.log

例如本次刚重启应用，日志修改时间却是数天前，应先确认输出路径是否正确。tail -f 按 Ctrl+C 结束查看，不会停止应用服务。

先确认日志修改时间和本次启动时间，避免用旧日志解释新故障。重点找本次启动后的首个实质错误及异常原因链，而非只看最后一条报错。

日志来源 常见位置与特点
应用文件日志 由 Logback 等框架决定，可能同时输出控制台和文件
nohup 控制台输出 未显式重定向且符合 nohup 的输出条件时，可能落到 nohup.out
systemd 日志 用 journalctl -u 查看，是否另写文件取决于应用配置
启动早期错误 可能发生在应用日志初始化前，应保留标准错误的可查入口

应用已有文件日志，仍出现 nohup.out，通常是控制台输出没有明确重定向。明确输出路径能消除文件位置歧义，但不会自动建立滚动和容量限制。控制台日志和框架日志需要分别检查保留天数、单文件大小、压缩和总容量策略。

11. 常见排障结论速查

问题 处理方向
脚本说 Java 已退出，jps 却仍有进程 核对完整命令与启动 PID，排查进程短名称误判
停止后马上启动提示端口占用 查真实监听 PID，等待释放，检查自动拉起机制
服务器本机可连，开发电脑不通 查绑定地址、防火墙、安全组、路由和来源限制
端口能连，应用仍报数据库错误 查账号权限、数据库名、协议版本和实际生效配置
Nginx 有响应，后端不可用 查代理目标、路径重写、上游端口和后端日志
服务在一台机器，依赖在另一台机器 localhost 指向当前机器，改查实际依赖地址及访问授权
修改本地配置后服务器行为不变 查部署包版本、外部配置、环境变量和启动参数
